## Phase Goal (user story)

**As a** visitor, **I want to** browse Rasmus's fully designed, responsive, accessible core site in my preferred theme, **so that** I can understand who he is, see his work, and reach him. This plan is the end-of-phase acceptance gate for that story.

<objective>
Run the phase-wide human verification of the completed core site. All implementation is done in plans 01-01 through 01-04 and gated by `npm run build`/`npm run lint`; this checkpoint verifies the things automation cannot fully prove — visual identity, real theme cross-fade, keyboard/AT behavior of the mobile overlay, cross-breakpoint responsiveness — and captures the user's confirmation of the discretionary homepage structure (D-07).

This closes: **DSGN-04** (distinctive Japanese-minimalist look), **DSGN-02** (dark/light with persistence + system default), **DSGN-03** (keyboard nav, focus behavior, reduced motion), **DSGN-01** (responsive across breakpoints).

Purpose: A design-and-accessibility phase needs a human eye before it ships; automated gates confirm it builds, not that it looks right or feels accessible.
Output: User sign-off (or a punch-list of issues that becomes a gap-closure plan).
</objective>

  </what-built>
  <how-to-verify>
    1. Run `npm run dev` and open `http://localhost:3000`.
    2. Homepage: confirm the hero shows name + role + one-line positioning + portrait + the "View My Projects" CTA, understandable without scrolling; scroll to confirm the featured-projects teaser (2-3 cards) links to `/projects`. Confirm this Hero + teaser structure feels right (D-07 is Claude's discretion — this is your explicit sign-off point per CONTEXT.md).
    3. Theme: click the header Sun/Moon toggle — confirm a smooth ~150-300ms cross-fade (not an instant snap), then hard-refresh (Cmd/Ctrl+Shift+R) and confirm the chosen theme sticks with NO flash of the wrong theme. Switch your OS between light and dark with the site freshly loaded (no stored choice) and confirm it follows the OS preference.
    4. Responsive: narrow the window below 768px — confirm the horizontal nav collapses to a hamburger; widen past 768px — confirm the horizontal nav returns. Check Home/About/Projects/Contact at mobile, tablet, and desktop widths.
    5. Mobile nav accessibility: at a narrow width, open the hamburger. Using ONLY the keyboard — Tab cycles within the overlay (focus does not escape to the page behind), Escape closes it, and focus returns to the hamburger button. Confirm the vermillion focus ring is visible on links/buttons as you Tab.
    6. Pages: read `/about` (three pillars read as one story), check `/contact` shows both a clickable "Email Me" mailto AND a visible plain-text email plus GitHub/LinkedIn links, and visit a made-up URL like `/does-not-exist` to confirm the custom "Page Not Found" 404 with a working "Back to Home".
    7. Identity: step back — does it read as distinctive Japanese-minimalist (generous whitespace, one focal thing at a time, sparing vermillion accent) rather than a generic dev-portfolio template (DSGN-04)?
    8. Optional: with OS "reduce motion" enabled, confirm the theme cross-fade and hover transitions are suppressed (DSGN-03).
    9. Known accepted gap: the `/blog` nav link 404s (Phase 2 ships it) — this is expected, not a bug.
  </how-to-verify>
